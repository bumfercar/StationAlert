# AI 활용 및 시행착오 기록

## 활용 원칙

AI는 코드를 대신 책임지는 도구가 아니라, 문서 확인과 반복 작업을 빠르게 수행하고
사람이 검토할 근거를 만드는 보조 도구로 사용합니다.

공식 API 동작과 실험 결과는 AI 답변만으로 결정하지 않습니다. 다음 순서로 확인합니다.

1. 현재 RTZR 공식 문서
2. 실제 실행에서 저장한 RTZR 응답
3. 사람이 직접 들으며 만든 정답
4. 테스트와 프로젝트 기록
5. AI가 제안한 내용

## 역할 구분

| 작업 | AI가 한 일 | 사람이 책임진 일 |
| --- | --- | --- |
| 요구사항 정리 | 요구사항과 제한사항을 표와 단계로 정리 | 제품 목표와 우선순위 결정 |
| API 조사 | 공식 문서 위치 확인, 문서 간 차이 비교 | 해석 검토와 최종 결정 |
| 코드 작성 | 작은 단위 구현과 테스트 실행 | 코드 이해, 변경 승인, 면접 설명 |
| 정답 데이터 | 라벨 형식과 검사 도구 제안 | 음성을 직접 듣고 정답 작성 |
| 실험 | 같은 조건의 반복 실행과 결과 집계 | 실험 범위 승인과 결과 해석 |
| Git | 변경 요약과 커밋 후보 작성 | 커밋·공개 승인 |

## 작업 방식

1. 파일과 Git 상태를 먼저 확인합니다.
2. 공식 문서로 확인한 내용과 아직 모르는 내용을 나눕니다.
3. 구현 전에 변경 파일, 이유, 다른 선택지, 확인 방법을 정리합니다.
4. 코드를 수정한 뒤 바로 커밋하지 않고 테스트를 실행합니다.
5. 실제 실패 내용도 지우지 않고 원인과 해결 방법을 기록합니다.
6. 기능과 테스트가 함께 완성된 시점에만 커밋합니다.
7. 실험에서는 설정, 입력 구간, 원본 응답, 코드 버전을 함께 저장합니다.

## 날짜별 기록

### 2026-07-16 — 빈 원격 저장소 시작 방식

- **상황:** 로컬 폴더는 Git 저장소가 아니었고 원격 저장소에도 commit이 없었습니다.
- **결정:** 첫 실행 가능한 기반만 `main`에 만들고, 이후 기능은 별도 branch에서 작업합니다.
- **이유:** 기준 commit이 없는 상태에서는 feature branch를 비교하거나 합치는 과정이
  오히려 복잡해집니다.
- **AI 활용:** 로컬과 원격 상태를 확인하고 예외적인 시작 방법을 제안했습니다.
- **사람의 판단:** 이 방식과 첫 구현 범위를 승인했습니다.

### 2026-07-16 — 비어 있던 Streaming 참고 파일

- **상황:** 전달받은 일반 STT 참고 파일에는 내용이 있었지만 Streaming 파일은
  0바이트였습니다.
- **결정:** 일반 STT 내용을 Streaming에 그대로 적용하거나 기억으로 채우지 않고,
  현재 RTZR Streaming·WebSocket·인증 공식 문서를 다시 확인했습니다.
- **확인 내용:** 필수 sample rate와 encoding, raw LINEAR16, 모델, 도메인, 키워드 제한,
  응답 필드, `EOS`, 토큰 유효기간을 확인했습니다.
- **남은 위험:** 문서와 실제 응답이 다를 수 있으므로 구현 후 안전하게 저장한 실제
  응답을 다시 기준으로 확인합니다.

### 2026-07-16 — M4A를 그대로 Streaming하지 않는 이유

- **상황:** 보유한 지하철 녹음은 M4A입니다. 일반 STT는 M4A 파일을 지원하지만,
  Streaming은 지원하는 형식의 audio frame을 받아야 합니다.
- **결정:** FFmpeg로 mono signed 16-bit PCM을 만들고 header가 없는 frame만 전송합니다.
- **다른 방법:** Python 내부 음성 decoding library 사용.
- **선택 이유:** 별도의 native package 설치 문제를 늘리지 않고, FFmpeg 명령과 결과
  형식을 직접 확인할 수 있기 때문입니다.

### 2026-07-16 — 공식 샘플 코드도 계약과 비교해서 사용

- **상황:** 공식 Python 예제는 WAV를 만든 뒤 파일 바이트를 읽는 형태인데, Streaming
  공통 문서에는 LINEAR16을 raw data로 보내라고 적혀 있습니다.
- **결정:** 예제 형태를 그대로 복사하지 않고 raw frame 계약을 따릅니다.
- **검증 계획:** 전송 첫 바이트가 `RIFF`가 아닌지 테스트하고, WebSocket으로 전달되는
  데이터를 별도 fixture로 확인합니다.
- **AI 활용 효과:** 공식 문서 여러 페이지를 비교하면서 header가 섞일 가능성을 구현
  전에 발견했습니다.

### 2026-07-16 — 실제 개발 환경을 먼저 확인

- **상황:** 기본 `python3`는 3.14.3이었지만 프로젝트에서 사용할 Python 3.11.15도
  설치되어 있었습니다. FFmpeg 8.1.1은 있었고 `uv`는 없었습니다.
- **결정:** `.python-version`으로 Python 3.11을 지정하고, `uv` 설치와 lock 파일 생성
  과정을 실제로 검증했습니다.
- **결과:** `uv` 0.11.29로 lock 파일을 만들고 `uv sync --extra dev`를 실행했습니다.
- **배운 점:** README 명령을 먼저 쓰는 것보다 실제 환경에서 성공하는지 확인한 뒤
  작성해야 재현성을 설명할 수 있습니다.

### 2026-07-16 — 제한된 실행 환경에서 설치 실패

- **상황:** 첫 dependency 설치는 PyPI 주소를 찾지 못해 실패했습니다. 이후 `uv`의 기본
  cache 경로도 실행 환경 밖이라 사용할 수 없었습니다.
- **판단:** package 버전이나 코드를 바꾸지 않고, 원인이 네트워크와 쓰기 권한 제한인지
  분리해서 확인했습니다.
- **해결:** 승인을 받은 네트워크 접근과 `.venv` 아래의 임시 cache로 동일한 설치와
  lock 명령을 다시 실행했습니다.
- **결과:** 전역 Python을 바꾸지 않고 저장소 내부 환경에서 설치와 검증에 성공했습니다.

### 2026-07-16 — 테스트가 찾은 Typer CLI 동작 차이

- **상황:** 최초 pytest에서 2개 테스트가 모두 실패했습니다. Typer는 command가 하나면
  이를 root command로 바꾸기 때문에 문서에 적은 `nextstop version`이 동작하지
  않았습니다.
- **수정:** root callback을 명시해 처음부터 command group으로 동작하게 만들었습니다.
- **이유:** 이후 추가할 `run`, `evaluate`, `report`와 동일한 CLI 구조를 유지하기
  위해서입니다.
- **결과:** 수정 후 pytest 2개, Ruff, `nextstop --help`, `nextstop version`이 모두
  통과했습니다.
- **배운 점:** 작은 CLI도 framework의 자동 동작이 사용자 명령을 바꿀 수 있으므로
  실행 테스트가 필요합니다.

### 2026-07-16 — 평가용 clip과 실제 데모 범위 혼동 수정

- **상황:** AI가 24개 평가용 clip의 검수 범위를 전체 원본의 연속 정답처럼 해석하고,
  원본 시작역도 노원으로 잘못 이해했습니다.
- **사람의 수정:** 24개 clip은 설정 비교용이고 실제 데모는 공릉부터 어린이대공원까지
  모든 방송이 담긴 원본 M4A 전체를 사용한다는 경계를 다시 확인했습니다.
- **수정:** 노원·중계·하계를 keyword와 상태 경로에서 제거하고, 공릉–어린이대공원
  11개 역만 허용했습니다. 범위 밖 목적지는 유료 API 호출 전에 거부합니다.
- **추가 관측성:** Streaming partial/final 수와 후보 수를 실행 중 표시하고, final 전사를
  선택적으로 출력하며, `Ctrl+C` 중단 시점까지의 응답도 비공개 artifact에 저장합니다.
- **배운 점:** AI가 만든 discovery set은 원본 데이터의 범위를 정의하지 않습니다.
  입력 범위와 정답 범위는 사람이 확인한 사실을 별도 source of truth로 고정해야 합니다.

### 2026-07-16 — 전처리 개선 실패와 도메인 후처리 분리

- **상황:** 먹골 20초 구간에서 RTZR는 목적지 keyword score 2.0과 3.0 모두 exact
  `먹골`을 반환하지 않았습니다.
- **전처리 실험:** 원본은 `막고니`, speech filter는 `마보니`, 100 Hz high-pass만 적용한
  filter는 `마콜`을 반환했습니다. 어느 전처리도 exact 역명 수를 늘리지는 못했습니다.
- **AI 제안:** `마콜`을 바로 `먹골`로 치환하는 대신 안내 문맥과 노선 후보를 함께 쓰는
  opt-in 음소 복원 규칙과 오탐 테스트를 만들었습니다.
- **테스트가 막은 오류:** 거리 비율만 사용한 첫 규칙은 `어린이비복원`을
  `어린이대공원`으로 잘못 복원했습니다. edit 절대 개수를 2개 이하로 제한해 긴 역명
  오탐을 차단했습니다.
- **실제 결과:** 동일 구간에서 RTZR 원문 `마콜`은 보존하면서 먹골 1건을
  `contextual_phonetic_recovery`로 추출했습니다.
- **해석:** 이는 STT 전사 성공이 아니라 지하철 문맥 후처리 성공입니다. 전처리는
  `none`을 기본값으로 유지하고, 복원도 `--recover`를 명시한 경우에만 사용합니다.

## AI 사용 시 지킨 제한

- AI가 만든 문장을 음성 정답으로 사용하지 않습니다.
- 측정하지 않은 숫자를 결과처럼 작성하지 않습니다.
- 유료 API 테스트는 명확한 opt-in으로 분리합니다.
- 비밀정보와 원본 음성을 AI 출력이나 Git 기록에 노출하지 않습니다.
- 성공한 작업만 남기지 않고 실패와 해결 과정도 기록합니다.
- 최종 코드와 설계는 사람이 설명하고 수정할 수 있어야 합니다.

이 과정에서 중요하게 보는 것은 AI가 작성한 코드 양이 아닙니다. 문서 간 차이를 일찍
찾고, 더 작은 단위로 검토하고, 실패를 재현 가능한 테스트로 바꾸는 데 AI를 얼마나
적절하게 사용했는지를 기록합니다.
